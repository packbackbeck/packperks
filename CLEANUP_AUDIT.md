## A. Security & money-path (backend / architecture)

### 🔴 A.1 — World-writable RLS on `claims`, `cup_balances`, `users` — **✓ verified live**
The database has its own built-in permission rules — called RLS (Row-Level Security), the database's own rules that decide who is allowed to read or write each individual row. A migration file that was meant to lock those rules down, `029_privacy_rls_lockdown.sql`, was **never applied** (never actually run against the live database). We confirmed this by inspecting the live rules table (`pg_policies`):
- On the `cup_balances` table, two rules — `cup_balances: anon update` **and** `cup_balances: authed update` — are set to `USING(true) CHECK(true)`, which is a permission rule that means "allow this for everyone, with no conditions." In plain terms: **anyone at all can set any customer's balance to any number.**
- On the `claims` table, the rule named `claims: anon update receipt path` has a condition that is literally just `true` (so the reassuring name is misleading — the name lies). This lets anyone **rewrite any column of any claim** — including `status='completed'`, `payout_amount`, and `tikkie_url`.
- Also on `claims`, the rule `claims: anon insert` is `CHECK(true)`, so anyone can forge a brand-new claim with any payout amount they choose.
- On the `users` table, `users: anon update` is `USING(true)`, meaning anyone can **rewrite another user's `auth_user_id`, which is effectively an account takeover** (pointing someone else's account at your own login); and `users: anon select USING(true)` lets anyone **read every user's email + IBAN** (bank account number).

Here "anon" means the public role every visitor's browser automatically uses before it logs in.

**The money path (how this turns into stolen cash):** inflate `cup_balances.balance` → submit a claim → that produces a large `payout_amount` → an admin approves it → `tikkie-cashback/index.ts:263` then pays out exactly `Math.round(claim.payout_amount*100)` of **real funds**. Because the amount was controlled by the attacker's browser, they choose how much real cash to mint.

**Why this is happening (and what it's for).** These wide-open `USING(true)/CHECK(true)` rules are the leftovers from the single-tenant, no-login prototype. Back when PackPerks was a device-id-only demo with no real Supabase Auth session, every visitor reached the database as the public `anon` role, and the app wrote to `claims`/`cup_balances`/`users` straight from the browser (the client-side inserts live in `src/lib/api.js`, A.6). To make that work at all, migration 012 and its siblings opened blanket grants (`to authenticated/anon using(true)`) — they "solve" the problem of a not-logged-in browser needing to create and update its own rows. Migration 029 was written precisely to retire this model — moving all writes behind trusted server-only functions (`service_role` edge functions — a `service_role` is the trusted server-only key, and an edge function is a small program that runs on Supabase's servers rather than in the browser) and limiting reads to only your own rows (scoped to `auth.uid()`, the unique ID of the currently logged-in user). But applying 029 was deferred ("DEPLOY-PENDING — authored offline", `029:4`) and, because 029 is itself broken (A.8), it never ran. So these too-permissive rules still keep the live app working: today's browser genuinely depends on anonymous write access to insert claims and update balances. That's exactly what you would break by deleting the rules cold — claim submission and cup crediting would stop for real customers until those writes are routed server-side (`create-claim`, `claim-cups`, `byo-mint`) and every visitor carries a real `auth.uid()`.

**How to fix it:**

1. Apply a corrected version of the lockdown all at once: allow writes only through trusted server-only functions (`service_role`), let people read only their own rows (owner-scoped selects keyed on `auth_user_id = auth.uid()`), and delete every wide-open anonymous rule (`USING(true)`). This is exactly what migration 029 is trying to do.
2. **✅ (recommended)** Roll it out in a safe sequence, following 029's own instructions in its header: first switch the app over to Supabase Anonymous Sign-in (which gives every visitor a real logged-in ID, `auth.uid()`, even if they never type an email), then move the remaining browser-side writes (A.6, C.5) to the server functions `create-claim`/`claim-cups`/`byo-mint`, then test the full customer and admin flows end-to-end on a throwaway copy of the database (a branch DB), and only then delete the too-permissive rules.
3. Fix the broken permission helper first (A.8) so the migration is even capable of running. And as an immediate, low-effort stopgap while the full lockdown is being staged, revoke anonymous UPDATE on just the single most dangerous columns right now — `cup_balances.balance` and `claims.payout_amount/status` — to shrink the money-path blast radius before the coordinated switchover.

**✅ Recommended: the staged rollout (option 2).** Ranked 2 > 3 > 1: option 2 stages the very same lockdown (anonymous sign-in → move writes to the server → swap the rules) on a throwaway copy of the database and closes the hole with no customer-facing outage; option 3 (fixing the A.8 helper plus the column-level revokes) is the immediate bridge that shrinks the money-path danger now but stays partial; option 1 (applying the lockdown cold, all at once) is correct in intent but deletes the anonymous writes the live app still needs, causing an outage.

**What it would cost (the trade-offs).** This is the "stop the bleeding" item, and the trade-off is entirely about the order you do things in, not about whether to do it. The lockdown itself is unambiguous — no one should be able to set another user's balance or rewrite a claim's payout — but it can't ship as a lone "delete the rule" (`drop policy`) command, because the live app still writes as the anonymous role; deleting the rules first and moving the writes later means a window where legitimate customers can't claim. The recommended path is the staged 029 rollout on a throwaway database copy (anonymous sign-in → server-side writes → swapping the rules), validated end-to-end before you promote it, because it closes the hole without a customer-facing outage. The stopgap column-level revokes are cheaper and buy time, but they're partial and easy to get subtly wrong — the API layer (PostgREST, the auto-generated API that sits in front of the database) silently reports "0 rows changed" when it blocks a write rather than throwing a visible error, which can hide breakage — so treat them as a bridge, not the fix.

### 🔴 A.2 — `app_config` writable by any authenticated user — **✓ verified live**
There is a settings table called `app_config`. One rule on it, `authenticated can manage app_config`, is set to `ALL USING(true) CHECK(true)` — meaning any logged-in session can do anything (read, write, delete) to it. A second rule, `public_read`, is `SELECT USING(true)`, meaning anyone can read the whole table — and it was never limited to only the public keys (`published:%`). Because of this, any anonymous-but-signed-in session can **rewrite the published settings for any org** (`published:<org>`) — including `cashbackRatePerCup` (the cashback rate per cup, read by `create-claim/index.ts:69-74`), `maintenanceMode`, or the published rewards — and can also read sensitive operational values like `tikkie:subscription` and the smart-bin config.

**Why this is happening (and what it's for).** `app_config` is the per-org key-value store that holds each org's published rewards and settings (`012:80`). The `authenticated can manage app_config … using(true) with check(true)` rule was created so the admin dashboard's org-creation wizard — which runs as an ordinary logged-in admin, not with the trusted server-only key (`service_role`) — could insert-or-update (upsert) the `published:<org>` entry right after creating a new org, and so that any admin could edit settings without someone having to write a custom permission condition (an RLS predicate). The wide-open `public_read` SELECT exists because the customer app must read each org's `published:<org>` config anonymously in order to show rewards and rates (`create-claim/index.ts:69-74` reads that same rate on the server). The oversight is that "authenticated" here really means any Supabase login session at all — including an anonymous customer sign-in — not "staff", and the read rule was never narrowed to `published:%`, so it also exposes operational secrets like `tikkie:subscription`. It solves a real need (the wizard's writes, and anonymous reads of published config) but it confuses who you are (identity) with what you're allowed to do (authorization).

**How to fix it:**

1. **✅ (recommended)** Allow only staff to write, and allow anonymous reads only for the public keys (`SELECT` restricted to `key like 'published:%'`). These are exactly the two rules that migration `029:84-90` already defines — `staff can write app_config` (gated by the `is_staff_admin()` helper) plus a separate `anon read published app_config` limited to `published:%`.
2. **✅ (recommended)** Because the org-wizard's upserts currently depend on the too-permissive rule, either move those writes into a trusted server-only function (`service_role` edge function, matching the `create-claim`/`generate-cups` pattern) or gate them on the corrected staff helper (A.8), so that tightening the write rule doesn't break org creation.
3. Move the truly-secret keys (`tikkie:subscription`, smart-bin config) into a separate table or key namespace that has no anonymous SELECT at all, so that even a read limited to `published:%` can never drift into exposing them.

**✅ Recommended: options 1 and 2 together.** Adopt 029's split — staff-only writes plus a read limited to `published:%` (option 1) — and, in the very same change, make sure the org-wizard keeps working via a `service_role` route or the fixed staff helper (option 2), so tightening writes doesn't break org creation. Option 3 (splitting the secret keys out of anonymous reach) is optional extra hardening.

**What it would cost (the trade-offs).** Cheap and low-risk relative to A.1 — `app_config` writes are admin-initiated and comparatively rare, so tightening them won't touch the customer hot path. The one migration concern is the org-creation wizard: if it writes `app_config` as a plain authenticated admin today, the staff-only rule must land together with either the `service_role` route or an `is_staff_admin()` that returns true for real staff, or org creation breaks. Recommended: adopt 029's two-rule split and confirm the wizard path in the same change; there's no meaningful downside to keeping secrets and cross-org writes out of rules that any logged-in session can reach.

### 🔴 A.3 — `tikkie-cashback create` can double-mint real money *(reported)*
In `tikkie-cashback/index.ts`, the code first checks whether a cashback already exists (lines `254-261`) and then, separately, sends the payment (the POST at `:289`). This is a "check, then act" pattern based on the `claim.tikkie_cashback_id` field — and the database index on that field is **non-unique** (it does not forbid duplicates), with no row lock. So if two `create` calls run at almost the same instant (an admin double-clicking Approve, or a retry), both read `null` (no cashback yet) and both send the payment → **the customer is paid twice.** (This is a race condition: two actions happening at the same instant that both slip through the check.)

**Why this is happening (and what it's for).** The `create` action was written to be idempotent (safe to run twice without actually paying twice), and its author believed the early exit on `claim.tikkie_cashback_id` (`254-261`) achieved that — the comment literally reads "Idempotent — never double-mint." In a world where everything runs one step at a time and one admin clicks once, that reasoning holds: read the claim, see no cashback id, POST once, store the id. The gap is that this "safe to run twice" guarantee was built as a read-then-write with a network call in the middle (the Tikkie POST at `:289`) and nothing at the database level to force the two calls into line — no row lock, and `tikkie_cashback_id` is a plain non-unique index. It solves the ordinary case but not concurrency, which is easy to trigger here: double-clicking Approve, an admin retrying a slow request, or bulk-approve (B.1) firing overlapping calls all produce two `create` invocations that both read `null` before either writes back, so both POST and the customer gets two live payout links.

**How to fix it:**

1. **✅ (recommended)** Make the claim update atomic (one all-or-nothing step): `update claims set tikkie_status='minting' where id=? and tikkie_cashback_id is null returning id`, and POST to Tikkie only if that UPDATE actually matched a row. The call that loses the race matches zero rows and returns the existing/minting state instead of paying again.
2. **✅ (recommended)** Add a partial `UNIQUE` index on `tikkie_cashback_id where tikkie_cashback_id is not null` (a database rule forbidding two rows from sharing the same cashback id), so even if two POSTs slip through, the second write-back collides instead of silently double-recording.
3. As a belt-and-braces backup, rely on Tikkie's own `referenceId` (already set to `claim.id`, `:271`) for provider-side idempotency if the Cashback API honors it, so a duplicate POST returns the same cashback rather than minting a new one.

**✅ Recommended: options 1 and 2 together.** The atomic check-and-update (option 1) is the core fix: it turns "check, then act" into a single, indivisible check-and-update (a compare-and-swap). The partial UNIQUE index (option 2) is cheap belt-and-braces in case a second POST still slips through. Option 3 (relying on Tikkie's own `referenceId`) is optional and can't be relied on alone.

**What it would cost (the trade-offs).** The atomic-claim guard (option 1) is a small, self-contained change with a large payoff — it converts a check-then-act into a single compare-and-swap and is the recommended core fix. Its one subtlety is that the `minting` marker (sentinel) must be reset on POST failure: the existing error path (`recordError`) already updates the claim on error, so it must clear the marker back to `null`, or a transient Tikkie outage would permanently wedge the claim as un-mintable. The UNIQUE index (option 2) is cheap insurance but requires confirming no existing duplicate/placeholder ids would violate it. Provider-side idempotency (option 3) is the most robust but depends on ABN AMRO's contract and can't be relied on alone. Recommend options 1 and 2 together.

### 🟠 A.4 — `tikkie-cashback create` never checks `status`/`type` before spending *(reported)*
In `index.ts:247-266`, the code reads the claim's `status` and `type` fields but never actually asserts that `status==='approved'` or `type==='cashback'` before paying. As a result, a real cashback can be minted for a **pending/denied** claim, or for a `direct_refund`/donation. The only thing currently stopping this is the admin UI — which can be bypassed.

**Why this is happening (and what it's for).** The server function was conceived as the trusted mechanical minter — "admin-invoked from the claims workflow" (`index.ts:5`) — with the business decision of whether a claim deserves payment delegated entirely to the admin UI (the `DecisionModal` and receipt-evidence gate, B.2). Under that division of labor the function only needs a claim id and an amount, so it deliberately doesn't re-litigate approval: it reads `status` and `type` into the row (`:248`), but the only checks before minting are that the claim exists, that `tikkie_cashback_id` is null (the idempotency/"don't pay twice" guard), and that `amountInCents > 0`. The flaw is that this edge function (the server-side function) is a directly reachable HTTP endpoint — any authenticated admin session can POST `{action:'create', claim_id}` for any claim id, bypassing the UI's gating — so a `pending`/denied claim, or a `direct_refund`/donation that shouldn't mint a cashback, can be paid.

**How to fix it:**

1. **✅ (recommended)** Assert the claim on the server before spending — reject it if the status isn't approved (`if (claim.status!=='approved') 409;`) and reject it if the type isn't cashback (`if (claim.type!=='cashback') 400;`) — so the money decision lives in the same code that moves the money, not only in the client.
2. **✅ (recommended)** Combine this with role-gating `create` (A.7), so it's not merely any admin but an authorized one who can invoke it.
3. Write the allowed states as an explicit allow-list of which `status`/`type` values the mint accepts, and log rejected attempts to the existing edge-function logs so probing surfaces. Note that `direct_refund` does legitimately mint via Tikkie elsewhere (C.3), so the `type` gate must permit whatever set the product actually pays — confirm the canonical vocabulary rather than hard-blocking every non-`cashback` type blindly.

**✅ Recommended: options 1 and 2 together.** Assert `status`/`type` on the server before spending (option 1), shipped with A.7's role gate (option 2) as one combined "protect the mint" change. Option 3 — encoding the payable states as an explicit, logged allow-list — is the disciplined way to pin the true approved-and-payable vocabulary that the trade-offs below flag as the only real work.

**What it would cost (the trade-offs).** Nearly free and unambiguous: a couple of guard clauses at the top of the `create` branch, no schema change, no client change. The only real work is pinning the exact status/type vocabulary the product intends to pay — the audit's `status==='approved'` must match what the approve flow actually writes (B.2 shows the inline quick-approve path writes `'completed'`), so the assertion set needs to cover the true approved-and-payable states rather than a single guessed value. Get that list right and there's no downside; get it wrong and you either still allow bad mints or start rejecting legitimate ones. Recommend shipping it together with A.7's role gate as one "protect the mint" change.

### 🟠 A.5 — `create-claim` never debits cups + no idempotency *(reported)*
In `create-claim/index.ts:75-89`, the code reads the balance, sets `cups_redeemed = full balance`, and inserts a `pending` claim — but it **never decrements the balance** (never subtracts anything from it) and never dedupes (never checks for duplicates). So a user can submit N claims off the same cups; if more than one is approved, the same cups pay repeatedly.

**Why this is happening (and what it's for).** `create-claim` is the server-authoritative claim writer built to replace the client insert (A.6), and its primary design goal was to stop the browser from setting its own `payout_amount` — it recomputes the amount from published config (`:69-83`). Debiting the balance was treated as a separate concern (the comment stack is all about amount authority and ownership, not ledger movement), and because a claim starts `pending` and only pays on admin approval, the author may have reasoned the cups aren't "spent" until then. So the function inserts the claim reading `cups = balance` but leaves `cup_balances` untouched, and has no dedupe on open claims. The gap is that nothing decrements the balance at any later point either, and nothing stops a user from submitting several `pending` claims that each read the same full balance — if more than one is approved, the same cups mint multiple payouts.

**How to fix it:**

1. **✅ (recommended)** Debit the cups in the same guarded, all-or-nothing operation as the insert — atomically `update cup_balances set balance = balance - :cups where user_id = :id and balance >= :cups`, and only insert the claim if the debit matched a row — which reserves the cups at submit time.
2. **✅ (recommended)** Enforce one open claim per user (a partial UNIQUE database rule, or a pre-insert check that no claim already has `status in ('pending','approved')`), so a user can't stack claims off one balance.
3. If the product prefers to hold cups until approval rather than at submit, move the debit into the approval/mint path — but keep it the same atomic guarded decrement keyed to the claim, so approval of a second claim finds the balance already spent and fails. This is the same atomic-ledger class as A.9/C.5 and should share that database routine (RPC).

**✅ Recommended: options 1 and 2 together.** Debit-at-submit (option 1) plus one-open-claim-per-user (option 2) makes the balance genuinely mean "unspent cups" and dissolves the multi-claim race — at the cost of a refund-on-denial path. Option 3 (hold-till-approval) is a valid alternative only if the product prefers it — same atomic decrement, but the displayed and actually-claimable balances diverge while a claim is pending.

**What it would cost (the trade-offs).** Moderate effort, because it forces a product decision — reserve cups at submit or at approval — each with UX consequences: reserve-at-submit means a denied claim must credit the cups back; hold-till-approval means the displayed balance and the claimable balance can diverge while a claim is pending. Debiting at submit (options 1 and 2) is the cleaner model and the recommended default: the balance then means "unspent cups" and the multi-claim race disappears, at the cost of a refund-on-denial path. Whichever is chosen, the decrement must be the atomic `where balance >= n` form, not a client- or read-then-write absolute, or A.9's lost-update race reappears. Low blast radius (one edge function), but it must land with A.1's lockdown, or the client can still bypass it via the direct insert (A.6).

### 🟠 A.6 — Claim creation is client-authoritative (bypasses the server) — **✓ verified**
In `src/lib/api.js:1095`, the `createClaim` function does a **direct client INSERT** (a write straight from the browser) into `claims`, with a **client-supplied `payout_amount`** — it never calls the `create-claim` edge function that was built to compute the amount on the server. Combined with A.1, the amount is attacker-controlled, and A.3 then mints it verbatim (exactly as stored). (See C.2 for the concrete direct-refund overpay this already causes with no attacker.)

**Why this is happening (and what it's for).** This is the original prototype claim path, and it still works because the anon RLS grants (A.1) let the browser insert `claims` directly. The client code is even self-aware about the lockdown it anticipates — the comments at `api.js:1096-1108` explain how it generates its own unique id (UUID) and sets `receipt_photo_path` at insert time specifically because the anonymous role holds INSERT permission but no SELECT permission on `claims`. In other words, `create-claim` (the server-authoritative replacement) was written and deployed, but the client was never cut over to it: the direct insert is the live path and the edge function is dormant. It "solves" claim submission today, but by trusting the browser to supply `payout_amount` (`api.js:1116`) — which is the entire vulnerability, because A.3's mint reads that stored amount verbatim, and C.2 shows the direct-refund path already stores the wrong amount even with no attacker present.

**How to fix it:**

1. **✅ (recommended)** Route all claim creation through the `create-claim` edge function (which recomputes `payout_amount` from published config, forces `status='pending'`, and verifies ownership) and delete the client insert path at `api.js:1095-1125`.
2. **✅ (recommended)** Do this in lockstep with A.1, so that once the client no longer needs anonymous INSERT on `claims`, the corresponding `using(true)` write policy is dropped — otherwise the direct path stays reachable even if the app stops calling it.
3. Point the existing callers (the `App.jsx` claim/refund handlers, folding in C.2's `refundRatePerCup` threading) at the server function, passing only `{user_id, org_id, reward_id, type, receipt_photo_path}` as its contract specifies (`create-claim:11-12`).

**✅ Recommended: options 1 and 2 together.** Route claim creation through `create-claim` and delete the client insert (option 1), wiring callers to its contract per option 3 — but it only closes the hole if it lands with A.1's anon-INSERT policy drop (option 2). Otherwise the direct path stays reachable no matter what the client calls.

**What it would cost (the trade-offs).** Low-to-moderate effort and clearly worth it: the edge function already exists and is deployed, so the work is client wiring plus deleting a function, not new backend. The one cost the code itself flags is latency — one extra edge round-trip per claim submit (~120-250 ms warm, ~1 s cold, `create-claim:15-17`) — a single spinner on a once-per-claim action, which is acceptable. The migration concern is that the cutover must be paired with A.1's policy drop, because leaving the anon INSERT policy in place means an attacker can bypass the server no matter what the client does. This is the linchpin of the "protect the mint" stage — recommend it alongside A.1/A.3/A.5.

### 🟠 A.7 — Money/mint endpoints under-gated *(reported)*
Three server endpoints don't check permissions tightly enough:
- `tikkie-cashback create` (spends real money) accepts **any** admin role; only `subscribe`/`unsubscribe` are owner-gated (`:238-240,410`).
- `generate-cups/index.ts:63-104` checks `status='active'` but **not role**, and trusts a caller-supplied `org_id` without a membership check → a manager in org A can mint spendable cups under org B.
- `delete-account/index.ts:38-93` erases a whole **cross-org identity** from one `device_id` match, with **no audit log**, and without clearing a live `tikkie_url` (an outstanding payout link).

**Why this is happening (and what it's for).** These three endpoints share an assumption that "authenticated admin/owner of a device" is a sufficient proxy for "authorized to do this specific privileged thing." `tikkie-cashback` gates only the webhook-subscription actions to `owner` (`:410`) because those touch account-wide config, while `create` was left at "any active admin" (`adminRow`, `:108-115`) on the theory that the UI only exposes mint to the right people (A.4). `generate-cups` accepts a caller-supplied `org_id` (`:98-104`) so the dashboard can mint cups for whichever org is active in a multi-org session — a genuine convenience — but verifies only that the caller is an active admin, never that they belong to that org. `delete-account` resolves the whole `identity_id` set (`:52-57`) to honor the shared-profile GDPR-erasure model across stores, and accepts device-id proof-of-possession (`:44-50`) because anonymous customers have no login token (JWT). Each solves a real need; each under-checks the authorization boundary around it — and `delete-account` nulls IBAN/receipt/AI fields on claims (`:66-68`) but leaves a live `tikkie_url`/`tikkie_cashback_id` intact and writes no audit row, unlike the merge functions.

**How to fix it:**

### 🟡 A.9 — Balance mutations race (lost updates / cap bypass) *(reported)*
In `share-cups/index.ts:119-134`, the code guards with `.gte("balance",count)` (balance must be at least the amount) but writes back a **stale absolute** value: two concurrent shares of 5 from a balance of 10 both pass, both write 5 → 5 cups conjured from nothing. In `byo-mint/index.ts:104-152`, the code reads `preBalance` then writes `preBalance+1`, and its daily cap is check-then-write → concurrent scans bypass it. The `cup_balances` table has no unique constraint and no row lock. (These are race conditions: two actions at the same instant that both slip through.)

**Why this is happening (and what it's for).** Both functions follow the same read-compute-write shape that reads naturally in JavaScript: fetch the current balance, compute the new value in the function, write it back. `share-cups` even adds a `.gte("balance", count)` predicate on the UPDATE (`:124`) and a compensating delete of the minted cups on mismatch (`:127-134`), so its author was clearly thinking about races — but the write still sets an *absolute* `newBalance` computed from the value read earlier, so two concurrent shares each read 10, each pass `.gte(...,5)`, and each write `5`, conjuring cups. `byo-mint` reads `preBalance` (`:114`) and writes `preBalance+1` (`:135-141`), and enforces its rolling-24h auto-credit cap by counting scans then writing (`:104-132`) — a check-then-write with no serialization. This shape exists because `cup_balances.user_id` has no UNIQUE constraint or row lock (the merge functions' own comments note "no UNIQUE, so ON CONFLICT is unavailable"), so there was no obvious atomic primitive to reach for.

**How to fix it:**

1. **✅ (recommended)** Replace each read-compute-write with one atomic relative statement — for `share-cups`, `update cup_balances set balance = balance - :n where user_id = :id and balance >= :n returning balance` (decrement inside the DB, not from a stale read); for `byo-mint`, a guarded increment plus a cap enforced in the same statement or via an INSERT-on-conflict against a per-window uniqueness key.
2. Add a UNIQUE constraint on `cup_balances.user_id`, so the increment/decrement can be an atomic upsert (insert-or-update) and duplicate balance rows become impossible (this also fixes the merge functions' inability to `ON CONFLICT`).
3. **✅ (recommended)** Wrap each mutation in a `security definer` plpgsql RPC (a database-side routine that runs with elevated/owner privileges) so the whole read-modify-write happens in one round-trip under row locks — shared by `share-cups`, `byo-mint`, `create-claim`'s debit (A.5), and the client reset path (C.5).

**✅ Recommended: option 1 now, option 3 as the target.** Ranked 1 > 3 > 2: option 1 (the atomic relative write) is the low-effort, low-risk baseline that fixes each site immediately; option 3 (the shared security-definer RPC) is the most robust and de-duplicates the same lost-update logic across A.5/A.9/C.5, worth building given how many findings share it; option 2 (the UNIQUE constraint) is a high-value enabler but gated on a one-time duplicate-row check first.

**What it would cost (the trade-offs).** The atomic-decrement rewrite (option 1) is low-effort and low-risk — `share-cups` already has the `.gte` guard and rollback scaffolding, so it's mostly changing an absolute write to a relative one — and it's the recommended baseline. Adding the UNIQUE constraint (option 2) is higher-value but needs a one-time data check first: the merge code claims "no user currently has duplicate balance rows," which must be verified before the constraint or the migration fails. The shared RPC (option 3) is the most robust and de-duplicates this logic across four call sites, at the cost of a little more upfront design; given how many findings (A.5, A.9, C.5) are the same lost-update class, the RPC is worth it. There's no reason to keep the stale-absolute writes.

### 🟡 A.10 — Merges are non-atomic *(reported)*
In `merge-by-email:203-300`, `admin-merge-users:196-290`, and `restore-by-email:188-265`, the merge does sum → write → repoint → delete → tombstone as many independent writes; repoint failures are swallowed into `repoint_errors`. A mid-way failure double-counts cups or orphans claims. (Here "tombstone" means marking the absorbed row as dead/merged; "repoint" means moving links from the old row to the surviving one.)

**Why this is happening (and what it's for).** The merges deliberately trade atomicity (all-or-nothing behavior) for partial-success resilience, and the code says so: `restore-by-email:216-218` explains that each table is repointed independently "because we want partial success to leave the system in a readable state — losing an activity_history row is much less bad than failing the whole merge and confusing the user." That instinct is defensible for a customer-facing restore where a hard failure would strand someone locked out of their cups. But the same shape got copied into all three implementations, and it means the sequence sum-balance → write-survivor → repoint-FKs (repoint the foreign keys — the links from one row to another) → delete-absorbed-balance → tombstone runs as many separate `service_role` (server-only) writes with no transaction: a crash or error after the balance is summed but before the absorbed balance is deleted double-counts cups, and a swallowed repoint error (collected into `repoint_errors` rather than rolled back) orphans `claims`/`cup_scans` pointing at a tombstoned row.

**How to fix it:**

1. **✅ (recommended)** Move each merge into a single `security definer` plpgsql function (an elevated-privilege routine in the database's own language) / one transaction, so sum-repoint-delete-tombstone either all commit or all roll back — no half-merged state, no double-count.
2. **✅ (recommended)** Consolidate the three near-identical implementations into that one routine (A.12) so `restore`/`merge-by-email`/`admin-merge` share the same transactional body and the same cross-org handling.
3. If a full transaction is too big a step, at minimum reorder so the survivor's balance is written only *after* the absorbed balance is removed, and treat any repoint error as fatal (roll back what you can) rather than logging and continuing — preserving today's resilience only for genuinely non-financial tables.

**✅ Recommended: options 1 and 2 together.** Do the transactional rewrite (option 1) and A.12's consolidation into one shared routine (option 2) as a single change, so you rewrite once and get atomicity plus uniform cross-org handling. Option 3 (reorder writes and treat repoint errors as fatal) is the partial fallback only if a full transaction is too big a step now.

**What it would cost (the trade-offs).** The transactional rewrite (option 1) is the correct fix and removes an entire class of ledger-corruption, but it's more than a one-liner: it means porting three TypeScript flows into plpgsql (or wrapping them in an explicit transaction via an RPC) and consciously deciding where the old "partial success is better than failure" philosophy still applies. The upside is large — these operate on real cup balances that map to real payouts — and merges are infrequent, so a transaction's added latency is irrelevant. The main risk is regressing the restore UX: a transaction that rolls back on a minor repoint failure could re-strand a user the old code would have limped through, so the function should still distinguish financial invariants (must be atomic) from best-effort cosmetic repoints. Recommend doing it together with A.12's consolidation so you rewrite once.

### 🟡 A.11 — `tikkie-webhook` is public, unsigned, and builds its URL from the body *(reported)*
In `tikkie-webhook/index.ts:61-95`: `verify_jwt=false` is correct (Tikkie doesn't send a login token), but there's **no shared-secret/HMAC** (HMAC is a cryptographic signature that proves the sender is genuine), and untrusted `n.campaignId` from the incoming request is interpolated straight into the outbound URL (`:84`). The re-fetch limits spoofing, but anyone can spray the endpoint to flip statuses and probe cashback IDs.

**Why this is happening (and what it's for).** The webhook is deliberately public and unauthenticated at the JWT layer — "verify_jwt MUST be false — Tikkie does not send a Supabase JWT" (`index.ts:14`) — which is correct for a third-party callback. The author mitigated spoofing by not trusting the notification body: the handler re-fetches the authoritative status from Tikkie before writing (`:79-95`), so a forged call can only set a claim to whatever Tikkie itself reports, and only for a `cashbackId` that already exists in the DB (`:72-77`). 3. Minimize the response surface (always return an opaque 200, as it already mostly does) and rate-limit, so the endpoint can't be used as a lookup tool (an oracle) to enumerate cashback ids.

**✅ Recommended: option 1.** Ranked 1 > 2 > 3: option 1 (verifying a path token/secret and building the re-fetch URL from the configured campaign) is the baseline that closes the spray/probe vector; option 2 (HMAC verification) strengthens origin proof but is nice-to-have and conditional on Tikkie actually signing callbacks; option 3 (opaque-200 + rate-limiting) is belt-and-braces oracle-hardening that's already mostly in place.

**What it would cost (the trade-offs).** Low effort and low risk — these are additive guards on an endpoint whose blast radius is already limited by the re-fetch, so even shipping just the path-token + configured-campaign change (option 1) meaningfully closes the spray/probe vector without touching the happy path. The one compatibility note is that adding a secret/token means re-subscribing the webhook with the new URL (a one-time `subscribe` call), and switching to the configured campaign requires confirming all live cashbacks belong to that one campaign (they should, given the single-campaign model). HMAC (option 2) depends on whether ABN AMRO/Tikkie actually signs callbacks — nice-to-have, not blocking. Recommend option 1 as the baseline; there's no reason to keep interpolating the body's `campaignId`, especially since A.13 wants a shared client anyway.

### 🟠 B.1 — Bulk approve silently swallows Tikkie mint failures — **✓ verified**
The "bulk approve" feature (the `runBulkAction` function at `AdminClaims.jsx:549`) approves many claims in one go. At `:550` it fires off all the approval calls together using `Promise.all(ids.map(updateClaimStatus…))` (a JavaScript pattern that runs all the calls at once and waits for them all to finish). But it never checks each result's `u.tikkie_error` field — the flag that says the payout link failed to be created. The single-approve path does check this, at `:465-469`. So a claim approved in a batch whose Tikkie payment link failed to generate still shows up as "Approved" even though the money never actually went out. (Tikkie = the payout-link service; "mint" = creating that payout link.)

**Why this is happening (and what it's for).** The single-approve path (the `handleStatusUpdate` function, `:465-469`) was deliberately built to show the `tikkie_error`, because `updateClaimStatus` hands back the claim record with a temporary `tikkie_error` field attached whenever the payout-link creation fails on the server side (the "edge function" — a small server-side function — at `adminApi.js:1638-1651`). The approval itself still counts, and the payout link can be retried later from the claim panel. Bulk approve (the confirm-popup flow labelled P-45 at `:538`) was added afterward so a reviewer can clear a whole queue of pending claims in one action with one shared reason. It reuses the very same per-claim `updateClaimStatus` call, but it only wired up the success case — folding the returned records into the on-screen state (`:552`) and writing one audit-log entry each (`:554-569`). Leaving out the error check is almost certainly an oversight of an incomplete copy-paste: whoever wrote it copied the state-merge and audit-log blocks from single-approve but not the error-checking block. And because in the normal situation (Tikkie campaign healthy, money available) every payout link succeeds, the gap never shows up in everyday use. It doesn't solve anything on purpose — the bulk path's real job (fast batch triage) works just as well with the missing check added.

**How to fix it:**

1. **✅ (recommended)** The fix the audit suggests: right after `const updateds = await Promise.all(...)` at `:550`, run `updateds.filter(u => u?.tikkie_error)` (i.e. pick out any results that carry a payout-link error) and, if any exist, show one combined error message via `setActionError(...)` that names the affected claim IDs / short codes and points the reviewer at the "Link failed — retry" badge — exactly like the single-approve message at `:468`. This is the smallest change and it closes the money-safety hole.
2. **✅ (recommended)** Go one step further and swap `Promise.all` for `Promise.allSettled`. With `Promise.all`, if one item in the batch throws an error, the whole batch is aborted and the others' results get thrown away too. `Promise.allSettled` instead waits for every item and reports each one's outcome individually — so one failed update (for example a permissions error, `RLS` being the database's row-level access rules, or a `claims_status_check` database-rule violation) no longer wipes out the audit-log entries of the claims that did succeed. Then sort the results into three buckets — succeeded / payout-link failed / threw an error — and report all three.
3. Show the failure on each individual row instead of only in a top banner. The state-merge at `:552` already spreads `byId[c.id]` (copies each claim's fields into the on-screen record), so writing `tikkie_error` onto each affected claim would automatically light up that row's Tikkie-status retry badge, leaving the combined `actionError` message as just a summary.

**✅ Recommended: (1) + (2) together.** (1) stops a failed *real* payout from masquerading as "Approved," with almost no chance of side effects. ### 🟠 D.1 — IBAN still embedded across DB + backend — **✓ verified (schema)**
