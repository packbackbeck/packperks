# PackPerks — Data Protection & Data-Flow Map (EU / UAE)

**Status:** DRAFT for internal review · **Prepared:** 2026-07-01 · **Scope:** the live PackPerks
customer app + admin console + Supabase backend as currently built.

> This is an engineering-accurate description of **what the system does today**, written so a
> reviewer (and, later, legal counsel) can assess GDPR (EU) and UAE PDPL obligations. It
> separates **as-built state** from **recommendations**. It is **not legal advice** — the lawful-basis,
> transfer-mechanism, and jurisdiction calls should be confirmed with a qualified DPO / counsel.
> Every table/field/policy below was read directly from the production database and codebase.

---

## 1. Systems, hosting & data residency

| Layer | Provider | Region / location | Notes |
|---|---|---|---|
| Database, Auth, Storage, Edge Functions | **Supabase** (project `ozvcpbthnauitaphosfb`) | **`eu-west-1` (AWS Europe / Ireland)** | Postgres 17. Primary store of all personal data. |
| Frontend hosting (SPA) | **Vercel** | Global edge/CDN (config-dependent) | Serves static JS/HTML only; no DB. Deploys from `main`. |
| Receipt AI verification | **Anthropic (Claude API)** | **United States** (`api.anthropic.com`) | Receipt **images** sent for verification (see Flow C). Cross-border transfer. |
| Transactional email (OTP / magic link) | **Supabase Auth** managed SMTP | Supabase-managed | Sends the 6-digit code / magic link to the user's email. |
| Source control | GitLab (`gitlab.com/packperks`) | — | Code only, no personal data. |

**Data residency headline:** the customer database + file storage are **in the EU (Ireland)**.
The only routine **egress outside the EU** is receipt images to **Anthropic (US)** during a claim,
and email addresses to Supabase's email relay for OTP delivery.

| Data | Where stored (table.column / location) | Sensitivity | Collection |

## 4. Core data flows

Legend: 🟢 in-EU (Supabase eu-west-1) · 🟠 leaves EU · 🔵 client device.

### Flow A — Anonymous onboarding & cup collection (default)
```
Customer browser 🔵
  │  generate packperks_device_id (localStorage)
  ▼
Supabase 🟢  INSERT users(device_id, org_id, display_name)  +  cup_balances(0)
  │  scan QR / deeplink → claim-cups edge fn (service role) activates cups, bumps balance
  ▼
Supabase 🟢  cup_scans (audit), activity_history, cup_balances
```
No email/IBAN required. Identity = `device_id`. **Personal data at this stage: device id + parsed device string only.**

### Flow B — Email save / verification (OTP)  *(optional, opt-in)*
```
Customer enters email 🔵
  ▼
check-email-save edge fn 🟢  (dedupe against existing accounts in the org)
  ▼
Supabase Auth 🟢 → signInWithOtp → email relay 🟠(email address only) → user's inbox
  ▼
User enters 6-digit code → session established → users.auth_user_id + email_verified_at set 🟢
  ▼ (if the email already had cups) merge-by-email edge fn folds accounts → one survivor
```

### Flow C — Receipt claim + AI verification  *(the main cross-border flow)*
```
Customer photographs receipt 🔵 (compressed to ≤800px JPEG client-side)
  ▼
Supabase Storage 'receipts' (private) 🟢   +   claims row (status pending)
  ▼
verify-receipt edge fn 🟢
  ├── base64 image → Anthropic Claude Haiku (moderation)      🟠 US
  └── base64 image → Anthropic Claude Sonnet (verification)   🟠 US
        payload = receipt image + target reward item name (NO email/name/IBAN/device)
  ▼
Anthropic returns verdict → stored in claims.ai_* 🟢
  ▼
Admin reviews/approves in console → payout status set 🟢
```
**Transfer point:** the **receipt image** (which can contain merchant, date, items, totals, and
incidentally any handwriting/faces on the receipt) is sent to **Anthropic in the US**. No account
identifiers are included in the payload.

### Flow D — Direct cash refund (IBAN)
```
Customer opens Direct Refund 🔵 → enters IBAN → validated client-side (ISO 13616 mod-97)
  ▼  cached in localStorage (packperks_user_profile) 🔵
  ▼  on confirm:
Supabase 🟢  claims(type=direct_refund, iban, payout_amount)  + users.iban
  ▼  Admin marks paid; actual bank payout is performed OUT OF BAND (not in this system)
```
The app **records** the IBAN and payout intent; it does **not** move money or call a bank/PSP API.

### Flow E — BYO stationary-QR mint (Phase 3)
```
Customer scans counter QR /<slug>/?byo=1 🔵
  ▼
byo-mint edge fn 🟢 (device/auth ownership check) → ≤2 cups/24h auto-credit,
  3rd+ → byo_cup_requests(pending) for admin approval. No new personal data collected.
```

### Flow F — Behavioural analytics
```
App UI events 🔵 → INSERT client_events(org_id, session_id, user_id, event, props) 🟢
No external analytics service. No IP / full URL stored.
```

### Flow G — Admin access
```
Staff → /admin → Supabase Auth (email+password / Google OAuth) → admin_profiles(role,status)
Row-Level Security scopes each admin to their org via current_admin(). Actions audited (IP, UA).
```

## 5. Analytics detail (`client_events`)

- **Destination:** Supabase table only. **No** Google Analytics / Segment / Mixpanel / Meta pixel.
- **Per-event fields:** `org_id`, `session_id`, `user_id` (the pseudonymous app user), `event` name,
  `props` (JSON — e.g. screen name, reward id, in-app-browser flag), `created_at`.
- **Entry context on app load:** `deeplink` type, `ref` tag, referrer **hostname**, `in_app` boolean
  (Instagram/Facebook/TikTok/etc. webview detection), `standalone` (PWA) — **no IP, no full URL.**

**localStorage keys set on the customer device:** `packperks_device_id` (UUID),
`packperks_user_profile` (**contains IBAN** + cached profile), `claimed` (UI flag),
`packperks_hiw_seen` (onboarding flag).

## 6. Security controls currently in place

- **Transport:** HTTPS/TLS everywhere (Supabase + Vercel default).
- **At rest:** Supabase-managed encryption (AWS eu-west-1); receipt/scan/donation buckets are
  **private** (`receipts`, `cup-scans`, `donation-receipts`) — served only via time-limited **signed URLs**.
- **Auth:** Supabase Auth (JWT). Admin console gated by `admin_profiles.status='active'` + role.
- **Edge functions:** run with the **service-role key server-side only**; the sensitive/admin ones
  (`admin-merge-users`, `invite-admin`, …) verify the caller is an active admin of an allowed role.
  Public customer functions (`claim-cups`, `byo-mint`, `check-email-save`) do **device_id / JWT
  ownership checks** instead of a JWT gate.
- **Secrets:** `ANTHROPIC_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY` are server-side only; the client
  ships only the **publishable anon key** + project URL.
- **Rate limiting:** `rate_limits` table + `check_rate_limit` RPC.
- **Input validation:** client-side IBAN checksum; receipt image size/type limits (≤10 MB, image
  MIME allow-list); a Claude **moderation** pass before receipt verification.
- **Admin audit trail:** `admin_action_log` (before/after state, actor, IP, UA); `admin_login_history`.
- **Account-merge PII scrubbing:** merging duplicate accounts clears the absorbed rows'
  `device_id / email / iban` (tombstoned via `merged_into`) — a partial data-minimisation control.

## 7. ⚠️ Current gaps & risks (honest assessment — for remediation)

Ordered by severity. These are **as-built findings**, to be weighed in the review.

1. **Permissive Row-Level Security on customer PII tables (highest priority).**
   The **anonymous** Postgres role — whose key is the *publishable anon key embedded in the public
   JS bundle* — currently has:
   - `users`: **SELECT / INSERT / UPDATE with `USING (true)`** → any holder of the anon key can read
     or modify **every** user row, including **email, IBAN, display name, device**.
   - `customer_identities`: **anon SELECT / INSERT / UPDATE `true`** → same (email, IBAN).
   - `cup_balances`, `cup_scans`, `activity_history`: **anon SELECT / INSERT / UPDATE `true`**.
   - `claims`: **not anon-readable** (good — SELECT is admin/owner only), **but anon INSERT and
     anon UPDATE are `true`** → a third party could insert/alter claim rows (integrity risk).

   **Impact:** emails, IBANs and names are effectively **not protected at the row level** — the
   RLS is demo-grade ("trust the client"). This is the top GDPR/PDPL security concern
   (Art. 32 GDPR "appropriate technical measures"). *Recommend: scope every customer table to the
   row's `auth.uid()` / verified device, and move all writes behind edge functions using the
   service role, before any real launch.*

2. **No cross-border transfer safeguard documented for Anthropic (US).** Receipt images leave the
   EU. Needs a DPA + transfer mechanism (SCCs / adequacy) and confirmation of Anthropic's
   retention/no-training terms. Same consideration for UAE users.

3. **No in-app consent / cookie mechanism.** Only essential Supabase Auth session cookies are set,
   but there is **no consent banner** and **no analytics-consent** choice. `client_events` runs
   without an opt-in. Assess whether the analytics constitutes "non-essential" processing requiring
   consent (EU ePrivacy) / notice + consent (UAE PDPL).

4. **No self-service data-subject rights.** There is no customer-facing **export** (portability) or
   **delete my account/data** flow. Admins can merge/soft-delete, but there is no documented,
   auditable **erasure** procedure fulfilling GDPR Arts. 15–17 / PDPL equivalents.

5. **No defined retention / deletion schedule.** Receipt & cup-scan images and claim/history rows
   are retained indefinitely; no TTL or purge job found. Financial (IBAN) and image data especially
   need a retention limit.

6. **IBAN cached in browser `localStorage` unencrypted** (`packperks_user_profile`). Convenient, but
   financial data persists on the device with no expiry.

7. **Privacy policy / terms are external links only** (`privacyUrl`, `termsUrl`, default
   `packperks.nl/privacy` & `/terms`) — content lives outside this repo. Must exist, be accurate to
   these flows, and name the sub-processors (Anthropic, Supabase, Vercel).

8. **`app_config` is publicly readable** (`public_read`). It holds org branding/copy/settings — no
   customer PII — but review it never accumulates contact details or secrets.

## 8. GDPR (EU) mapping

| Requirement | Current state | Action |
|---|---|---|
| **Lawful basis** (Art. 6) | Not documented per purpose | Define: contract (cups→cashback, refund/IBAN), legitimate interest or consent (analytics), consent (optional email) |
| **Transparency** (Arts. 13–14) | External privacy URL only | Publish a policy covering these exact flows + sub-processors |
| **Data minimisation** (Art. 5) | Good defaults (anon by default; email/IBAN optional); merge scrubs PII | Add retention limits (§7.5) |
| **Security** (Art. 32) | TLS + private buckets + admin RBAC **but** permissive anon RLS (§7.1) | **Fix RLS** — top priority |
| **Data-subject rights** (Arts. 15–22) | No self-service export/erasure | Build export + delete; document manual DSAR SLA |
| **Records of processing** (Art. 30) | This document is a starting point | Formalise ROPA |
| **International transfers** (Ch. V) | EU-hosted DB; **receipt images → Anthropic US**; email → Supabase relay | SCCs/DPA with Anthropic + Supabase; document |
| **Processor agreements** (Art. 28) | Assumed, not verified | Sign/verify DPAs (Supabase, Anthropic, Vercel) |
| **DPIA** (Art. 35) | Not done | Likely warranted (financial data + image processing + AI) |
| **Breach process** (Arts. 33–34) | Not documented | Define 72-hour notification runbook |

Data are hosted in the EU (Ireland) — a favourable starting point; the main EU exposures are the
**anon-RLS gap**, the **Anthropic transfer**, and the **rights/consent/retention** process gaps.

## 9. UAE (PDPL) mapping

Reference: UAE **Federal Decree-Law No. 45 of 2021 (PDPL)**. *(If PackPerks operates through a
free-zone entity — DIFC or ADGM — those zones have their own data-protection laws that may take
precedence; confirm the operating entity — see §11.)*

| Theme | Current state | Action |
|---|---|---|
| **Consent / notice** | No in-app consent; external policy | Provide clear notice + consent for UAE users, esp. analytics + email |
| **Cross-border transfer** (PDPL Arts. 22–23) | UAE customer data would sit in **EU**, and receipt images go to **US** | Rely on adequacy/appropriate safeguards; document the transfer basis; consider consent |
| **Data-subject rights** | None self-service | Provide access/correction/erasure/objection handling |
| **Data residency** | No UAE-resident copy | Assess whether any sector rule requires local storage; otherwise document the EU/US transfer |
| **Security measures** | Same as §6 + the §7 gaps | Same remediation (RLS first) |
| **IBAN / financial data** | Stored for refund intent only; no payout execution here | Confirm any UAE payments/financial-data rules if refunds run to UAE accounts |

## 10. Retention & deletion (current vs. recommended)

| Data | Current | Recommended |
|---|---|---|
| Receipt / cup-scan images | Indefinite (private buckets) | Delete N days after claim decided (e.g. 90d) |
| Claims (incl. IBAN) | Indefinite | Keep financial records per tax/audit rule; then purge/anonymise IBAN |
| `users` / `customer_identities` | Indefinite until merge | Erasure on request; inactivity purge policy |
| `client_events` analytics | Indefinite | Rolling window (e.g. 12–24 months), then aggregate/drop |
| Admin audit / login logs | Indefinite | Security-retention policy (e.g. 12 months) |

Existing minimisation: **account-merge clears** absorbed rows' `device_id/email/iban`.

## 11. Open questions for the reviewer

1. **Controller model:** is PackPerks the sole controller, or joint/independent controllers with
   each client brand? (Drives DPA direction + policy wording.)
2. **Operating entity & jurisdiction:** EU entity? UAE mainland vs **DIFC/ADGM** free zone? (Selects
   PDPL vs DIFC/ADGM DP Law, and transfer analysis.)
3. **Are DPAs signed** with Supabase, Anthropic, and Vercel? Any zero-retention terms with Anthropic?
4. **Analytics basis:** treat `client_events` as essential product telemetry (legitimate interest) or
   consented analytics?
5. **Retention periods** the business wants for images, claims/IBAN, analytics, logs.
6. **Payout execution:** which bank/PSP actually pays the IBAN refunds (that processor is out of this
   codebase but in scope for the overall data map)?
